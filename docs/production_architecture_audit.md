# Production architecture audit

Audit date: 2026-11-06. This audit inspects the working tree, including uncommitted additions, rather than assuming the October 31 report describes today's implementation. The earlier report is `docs/project_structure_report.zh-CN.md` and identifies baseline `070c12d`. Current Git HEAD is still that commit (its Git author date is June 29); there is no committed October 31-to-present history to attribute chronologically. Differences therefore mean current tracked changes and untracked source against that baseline, not an invented sequence of releases. Working-tree and source evidence is under `runs/runtime_foundation/audit_20261106/`.

**Conclusion:** substantial strategy, state, risk, execution and accounting implementations exist, but their runtime ownership was fragmented across research executables. A first native runtime now joins the existing combinatorial pipeline and supplies a durable, conservative paper lifecycle. This is a production foundation, not production acceptance. Market making and cross-venue strategies retain their existing behavior and are not yet enabled plugins in this executable. External account reconciliation and network feed integration remain release blockers.

## Scope and classification

IMPLEMENTED means executable logic exists and relevant current tests exercise it, not that it is exchange-certified. PARTIALLY_IMPLEMENTED means useful functionality with a material lifecycle/integration gap. SKELETON means placeholders. DUPLICATED means overlapping implementations or owners. UNVERIFIED means the production property is not established by this audit. A subsystem can have a primary classification and a separate ownership issue.

## Traced call paths

1. Original default: `engine/main.cpp → RealtimeFeedEngine::run → WebSocketClient callbacks → RawLogWriter`. There was no strategy/risk/OMS/ledger lifecycle at that entry.
2. Existing bundle tool: `tools/run_worldcup_feed_to_execution.cpp` receives WS → `DecodePipeline` → `MarketStateStore` → `SignalEngine` → `OrderDecisionEngine` → `RiskEngine::evaluate_decision` → approved envelope → `ExecutionGateway::submit_approved_decision` → `PaperExecutionAdapter` → report publisher → `PaperTradingEngine`. Tool-local publishers and shutdown own the wiring; it is not a reusable supervisor.
3. Existing maker tool: `run_market_maker_dashboard_live.cpp` → MM/product fair/quote generation → `QuoteRiskEvaluator::evaluate` → `PaperMakerExecutionAdapter::submit_approved_quote` / cancel groups → `PaperLedger::apply_fill`. The tool maintains its own runtime and accounting state.
4. Cross-venue: research CLI → discovery/capture or `LiveL2Replay`/generalized replay → approved pair/payoff proof and synchronized store → opportunity and multi-wallet reservation → simulated pair execution → `TwoAccountPaperLedger`. It does not route executable pair legs through one shared OMS today.
5. New first slice: both `trading_engine` and `trading_runtime` entrypoints → `runtime::run` → frozen config/artifact + journal → recorded `RawPacket` → `DecodePipeline` → `MarketStateStore` → `CombinatorialPlugin/SignalEngine` → `OrderDecisionEngine` → existing portfolio guards + `RiskEngine` → durable submit marker → existing `ExecutionGateway` → existing `PaperExecutionAdapter` → durable reports → existing `PaperTradingEngine/PaperLedger` → atomic dashboard → existing backend and dashboard.

## Accountable owners

| Object | Authority in new slice | Conflicting/current alternative | Required contract |
|---|---|---|---|
| Market book | Single `MarketStateStore`; read through `MarketStateView` | Cross-venue store; legacy feed/state | One venue-qualified ingestion owner; derived as-of views cannot create independent truth. |
| Strategy intent | Plugin produces; supervisor deduplicates native idempotency hash | Tool-local publication/dedup | Strategy ID + immutable provenance; no adapter access. |
| Risk reservation | One `RiskEngine/ReservationBook` | Maker outstanding quotes and per-wallet research ledgers | Atomically admit all strategies using accounted positions plus open/unknown orders. |
| Orders | `ExecutionGateway` plan/order IDs; durable runtime lifecycle evidence | Maker active quote book; simulated pair state | Extend gateway for typed maker/bundle/pair requests rather than replace it. |
| Fills | Paper adapter's delta reports, durably recorded before accounting | Chain hints, public trades, simulated pair receipts | Only authoritative source can advance fills; public hints never become own fills. |
| Positions/cash | `PaperLedger` through `PaperTradingEngine` | Separate marked `PaperPortfolio`, runner ledgers | Ledger is quantity/cash authority; mark projections must reconcile to it. |
| PnL | Existing `PaperPnLEngine` and dashboard projections | Lead-lag and cross-venue research PnL | Tag valuation vs conditional terminal guarantee vs settled/received cash. |
| Exchange balances/settlement | No authority connected | Public metadata and chain hints insufficient | Report `exchange_account_reconciled=false`, live realized PnL null. |
| Recovery | Hash-chained journal + frozen original inputs/artifact/binary | Tool-local JSON/CSV files | Complete deterministic prefix; incomplete submit freezes and restores durable receipts. |

## Material gaps and conflicts

- Existing bundle risk generally tracks outstanding reservations, not all already acquired positions or cash. Per-runner policy instances are not a global portfolio limit. The slice projects its existing ledger into existing guards; cross-strategy/account aggregation remains migration work.
- `RiskEngine` converts decision legs to unit bundle ratios for its historical repricing/reservation contract. The runtime explicitly checks actual sized lots with existing `InventoryGuard` before that call. One in-flight atomic paper plan avoids exposing understated open-lot reservations; do not generalize this to concurrent or asynchronous orders.
- `ExecutionGateway` historically prepares children/plans as Acked before adapter results. The runtime labels its observer event `PLAN_PREPARED`, not an exchange acknowledgment. Gateway's direct `submit(plan)` bypasses the fuller managed path. Neither is acceptable as the basis for future live order truth without extension.
- Gateway `poll()` drains pending local reports, rather than providing a full live async receive/reconcile loop. `cancel_plan` uses mode-specific cancellation and must not be interpreted as exchange confirmation without authoritative adapter receipt. New slice uses no external cancel/settle path.
- `FillTracker` previously counted duplicate delta reports twice; fixed here with regression coverage. Current legacy reports lack a native exchange fill ID; identical tuples can collide. Future live adapters must carry authoritative unique fill IDs and normalize cumulative counters before deduplication.
- Reservation TTL release alone cannot establish that an externally submitted order is dead. The runtime freezes incomplete/unknown work and does not advance to another evaluation. TTLs are not used as proof of external cancellation.
- The first slice exposed pre-order mark aliasing: `PaperTradingEngine` learned asset indices only from later order plans. The runtime now binds validated artifact indices before the first mark; an asymmetric-price regression checks valuation and restart. Existing strategy behavior is unchanged.
- `PaperLedger` and `PaperPortfolio` both hold positions. One is canonical cash/quantity; the other is a marking projection. The slice reads risk from the ledger. Their generic internal reconciliation still needs an explicit invariant.
- Read-only dashboard availability is not feed freshness, account reconciliation or business health. Recorded replay timestamps are logical time; measured processing latency is local and includes journal persistence. There is no claim of synchronized live L2 from this exercise.
- Recovery requires the identical executable, frozen inputs and artifact. It detects corruption and blocks a torn tail rather than silently repairing it. It has no externally anchored/WORM integrity proof or broker-side recovery authority.
- First slice supports only one combinatorial plugin, uncompressed Polymarket-format recorded inputs and one synthetic paper account. PAPER currently means paper execution of bounded recorded input; SHADOW means identical decisions/risk with no adapter submissions. Live feed paper, maker execution unification, multi-wallet runtime and exchange reconciliation are recommendations, not delivered capabilities.
